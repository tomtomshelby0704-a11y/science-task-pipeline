# tb-run：执行题目

## 触发口令

- `执行题目 <题号>`：在执行单元（Codex）里，把一份已登记的选题做成题包，跑完工程检查和模型校准，整理证据，登记台账。可附候选号：`执行题目 tbs-003 候选 2`。
- `持续执行`：执行单元自己从题库领题，逐题走完下面的“步骤”，领不到题才停。领题规则见“持续执行的领题规则”，中途何时才允许停见“推进深度”。达标题登记后由第 10 步**自动审查**：另起独立 Codex 进程按 [tb-review](../tb-review/SKILL.md) 审；材料类退回自己修，最多 3 轮；通过就归档到本机 `deliveries/`。人类不用说 `审查`。

## 目的

覆盖要求书第二、三、四阶段。本 Skill 只规定做什么、产物放哪、判据在要求书哪一节；具体技术做法由执行单元按要求书自行决定。

## 持续执行的领题规则

收到 `持续执行` 时，用下面的规则代替步骤 1 的“人类给题号”，步骤 2–10 不变。同一台机器可以同时开多个做题对话，各自 `持续执行`，它们会自动领到不同的题（各题产物目录 `tasks/<题号>/` 互不重叠，Docker 共用）。

1. 按 AGENTS.md [规则同步](../../AGENTS.md#规则同步) 做一次同步动作（含 `git pull --rebase origin main`），再做一次下面“本机复检”；按 [queue.md](../../flows/tb-science/topics/queue.md) 从上到下，取第一个**可领**的题。可领的定义只有三种：`topics/<题号>.md` 头部状态**恰好**是 `待执行`，或是 `待执行（退回，<本机名>）`，或是 `待执行（重判，<本机名>）`，或是 `待执行（补测强模型，<本机名>）`。其他任何状态一律跳过取下一题：`执行中（…）`（不论括号里是哪台机器，**包括本机**，那是本机另一个对话在做）、`阻塞（…）`、`已执行-*`、别的机器的退回、重判或补测。queue.md 不存在或里面没有可领的题，退回取**题号最小**的可领题。没有 → 回报一行 `<机器名> 空闲：无待执行题目`，结束。人类登记新题后再说一次 `持续执行`。领走后不改 queue.md。
2. 候选起点取该题头部的 `起始候选`，没有该字段从候选 1 起。
3. 按步骤 1 占题（状态改 `执行中（<机器名>）`，push）。push 被拒 → pull 后重读状态；状态已不是可领 → **不论占者是谁（包括本机的另一个对话），换下一题，不回报**。`持续执行` 里永远不触发 AGENTS.md 并发规则 4 的“撞上就停”；“撞上就停”只在人类点名 `执行题目 <题号>` 时适用。
4. 走步骤 2–10。第 9 步、第 10 步的回报照常发出，然后**不等人类**，直接回到第 1 条领下一题。手动 `审查` 退回的题会出现在 queue.md 第 1 位、状态 `待执行（退回，<本机名>）`，由本机下一轮领走，按第 1 步修复后同样进入第 10 步。
5. **退回止损**：第 1 条取到的题如果头部已有 **3 行或更多** `- **退回**：` 记录（第 10 步的修复轮与手动审查的退回一起算），不再领取：把状态改为 `阻塞（<机器名>）：审查修复 3 轮仍退回；解除条件：人类看最新一份 reviews/<题号>-rN.md 决定修或弃`，commit，push，回报该文件的 `blob` 链接，然后继续取下一个可领题（不停循环，这不是本机故障）。
6. 中途遇到障碍（Harbor 跑不起来、依赖装不上、网络断、Codex 凭据不可用、Docker 异常、题包跑不通等）→ 按下面“推进深度”处理：**不到门槛不标阻塞、不停、不问人类**。到门槛后：障碍只属于本题 → 标 `阻塞` 后继续领下一题；障碍属于本机（所有题都做不了）→ 标 `阻塞` 后停止循环。人类处理后对任一执行机说 `执行题目 <题号>` 或再说 `持续执行`（阻塞的题不会被 `持续执行` 领走）。

## 本机复检（领题前，约 1 分钟）

环境问题在机器层面修，不在题里修。`持续执行` 每轮领题前、`执行题目` 占题前各做一次：

1. 读 `{{WORKDIR}}/environment-check.md`（格式见“推进深度”第 6 条）和 `{{WORKDIR}}/env-kit/` 清单；
2. `docker info` 正常返回。

不过属于**本机故障**：
- 先按“坑与修法”表自愈。例如 Docker Desktop 引擎掉线：Windows 上 `wsl --shutdown` 后重启 Docker Desktop。
- 修好再领题。自愈期间不占题，不改任何题的状态，不产生运行记录。
- 自愈到“推进深度”门槛仍不行，按门槛处理。

## 推进深度（何时才允许停）

适用于 `执行题目` 和 `持续执行` 的全过程，也适用于启动 prompt §0 的环境安装。执行单元的默认姿态是把题做完，不是遇到问题就交给人类。

1. **中途不问、不等**：不向人类发“是否继续”“要不要换方案”之类的询问，不停下等确认。回报只在三个时刻发：第 9 步题目登记完成、第 10 步审查有结论，或达到下面的停止门槛。
2. **遇到障碍先自己推进**：查日志、查官方文档、换做法。只有**实质不同**的做法才算一次尝试（重跑同一命令、改一个无关参数不算）：例如依赖下载断 → 换镜像源 / 换版本 / 先下 wheel 再离线装 / 换等价工具；远端 push 失败 → 换协议或重试间隔；Harbor 报错 → 读源码或 issue 换参数；容器内 Codex 连不上推理服务 → 换凭据传入方式或核对放行域名。
3. **障碍只卡一条路时，其他路继续走**：先做所有不依赖它的步骤，再回头。典型：`git push` 不通 → 继续本地工程检查和校准运行，每 10–15 分钟重试一次 push，题结束前补推；某个依赖装不上 → 先把不需要它的子检查、数据生成做完。
4. **停止门槛**（任一成立才允许标 `阻塞`）：同一障碍连续推进墙钟 **≥ 6 小时**仍未解决；或已尝试 **≥ 10 种**实质不同的办法仍未解决。门槛之前只有一种例外可以提前停：剩下的**每一步**都依赖人类亲手操作（管理员密码、GUI 点确认、付款、缺失的凭据），且不依赖它的事已全部做完。
5. **到门槛后的处置**：把题状态改为 `阻塞（<机器名>）：<题目不可用 / 本机故障>——<原因>；解除条件：<要人类决定或做什么>`，并在 `topics/<题号>.md` 本机执行记录里写**尝试清单**：墙钟起止时间，每种办法一行（做法、结果、日志的本机路径）。commit，push，回报该文件的 `blob` 链接。“题目不可用”指障碍出在这道题自身（草稿跑不通、数据构造不成、验证器无法做到参考解过而简化不过等），别的题不受影响；“本机故障”指所有题都做不了。
6. **踩坑经验落本机，同一个坑不 debug 第二次**：
   - `{{WORKDIR}}/environment-check.md`（本机，不进仓库）固定三节：
     - `## 当前环境`：版本、启动 prompt §0 两条验收的结果与时间；
     - `## 坑与修法`：表格，列为日期、现象（报错原文关键字）、根因、修法、可复用产物、验证方式；
     - `## 可复用产物`：`{{WORKDIR}}/env-kit/` 里每个文件的用途。
   - `{{WORKDIR}}/env-kit/` 放修好且验证过的可复用件，如预装被试 agent 工具的 Dockerfile 段、带绝对路径的 docker 启动脚本、强模型的 harbor 命令封装（密钥从 `.env` 读）、apt/pip 重试或镜像配置。新题要用就从这里复制，不从旧题目录里翻。
   - 遇到环境报错，**先按报错关键字查“坑与修法”**，有就照做；查不到才按本节第 2–4 条推进。修好**当场**补一行，有可复用件就放进 `env-kit/`，不等题结束。
   - 坑表有新行时，把脱敏后的“坑与修法”表同步为仓库 `flows/tb-science/boot/<机器名>-environment.md`（台账类，直接推 `main`）。遇到没见过的报错，也先查同系统其他机器的这个文件。
   - 发现 Skill 写法与本机实际不符，写进第 9 步回报，由云端 Claude 改规则，执行单元不改规则文件。

## 省力协议（等待与输出）

长时间运行（强模型一次 25–40 分钟）期间反复查看，每次都要把整段对话历史重发一遍，token 消耗最大。本节规定怎么等、看什么、输出多少。适用于 `执行题目` 和 `持续执行` 的全过程。

1. **测一次本机阻塞上限**：本机首次校准前，依次跑 `python3 repo/skills/tb-run/scripts/wait_runs.py --probe 1800`、`--probe 900`、`--probe 300`。能原样返回 `probe ok` 的最大秒数记作 `MAX_BLOCK_SEC`，写进 `{{WORKDIR}}/environment-check.md` 的“当前环境”一节，之后不再测。同一节再记 `MAX_PARALLEL_RUNS`，即本机同时跑几次强模型不会内存或磁盘不足，默认 2；出现过内存耗尽的机器按实测调低。
2. **成批发起，一次等完**：第 5 步的 GPT 5.6 四次运行在后台同时发起，最多并行 `MAX_PARALLEL_RUNS` 个，每次一个运行目录 `runs/<候选号>-gpt56-<k>/`，发起命令用本机 `env-kit/` 的封装。发起后只用一条命令等：
   ```
   python3 repo/skills/tb-run/scripts/wait_runs.py <这一批的运行目录...> --max-wait <MAX_BLOCK_SEC>
   ```
   - 返回 3（时间到了、还有在跑的）→ **原样再调一次**，中间不夹别的命令。
   - 返回 0 → 这一批全部结束，接着发起下一批。
   - 返回 4 → 有运行卡住或目录不存在，按第 4 条看细节。
3. **等待期间不做三件事**：不查看日志、容器或运行目录；不在对话里写“还在跑 / 还没完”这类进度话；不重读规则文件。Codex 中途把控制权交回来、命令仍在后台跑时，继续等，不做别的事，也不写说明。
4. **只在三种时候看细节**：`wait_runs.py` 返回 4；某次运行结束后写它的 `summary.md` / `metadata.json`；第 6 步判定。看的时候遵守第 5 条。
5. **输出上限**：
   - 每条命令的输出不超过 40 行，用 `| tail -n 40` 或 `grep` 截取；
   - 不 `cat` 整份 `trajectory.json`、`result.json`、`job.log` 或题包里的大文件；
   - 步数和 reward 用 `wait_runs.py` 或 `check_delivery.py` 的函数数，不靠肉眼翻 JSON；
   - 查报错只看最后 60 行，再加一次 `grep -n -i "error\|exception\|traceback"`。
6. **读文件不重复**：
   - 规则文件只在“规则同步”列出改动时重读，领新题时不重读整份要求书和 Skill；
   - 题文件只读当前候选和构建简报；
   - 同一个大文件一轮里只读一次，要用的结论记进检查点。
7. **用本机检查点代替对话记忆**：每题维护 `{{WORKDIR}}/tasks/<题号>/checkpoint.md`，每个阶段写一行（时间、阶段、关键结果、下一步）。阶段包括占题、构建完成、工程检查、每批运行的发起与结束、判定、登记、审查。对话被压缩或中断后，从检查点接着做，不翻历史、不重跑。
8. **等审查也一样**：第 10 步起的 `codex exec` 审查进程阻塞等待，规则同第 3 条。

## 达标版本保护

合规的达标轨迹很难跑出来，重跑通常跑不回来。所以一个版本一旦达标，它的题包和判定用的运行就冻结，后面的任何修复都不能把它弄坏。起因见 tbs-020：v2 达标，为补一条审查意见改出 v4 重跑，结果不达标。

1. **冻结**：第 8 步对达标版本 `check_delivery.py` 得 `ok` 后，立即：
   - 把 zip 复制到 `{{WORKDIR}}/deliveries/frozen/`，设为只读（Windows `attrib +R <文件>`，macOS / Linux `chmod a-w <文件>`）；
   - 在 `topics/<题号>.md` 头部加一行 `- **达标版本**：v<N>；冻结 zip <路径>；SHA-256 <值>；判定运行 <运行=判定，…>`，随第 9 步推送。
   判定用的本机运行目录 `runs/<候选号>-<模型>-<序号>/` 从此只读，不移动、不改名、不重写 `metadata.json`。
2. **不覆盖**：冻结 zip 和判定用运行目录不得覆盖、删除或重打包。每次要动这道题之前，先核对冻结 zip 存在且 SHA-256 与题头一致；不一致就标 `阻塞（<机器名>）：达标版本保护——冻结包缺失或被改` 并停。
3. **重判或修复只从冻结 zip 起步**：本机工作目录 `候选<N>/package/` 可能已经是更新的版本。题头有 `达标版本` 时，第 1 步的重判和退回修复一律以冻结 zip 为准，不得从工作目录重打包。材料类修复需要新包时，用冻结 zip 里的 `task/` 和 `runs/` 原样加上改过的材料重打包。打完对比新旧两份 `MANIFEST.json`：除本轮修的文件外，哈希必须全部相同，否则作废新包。新包 `ok` 后另加一行 `达标版本`，旧冻结包保留。
4. **题面类退回不自动修**：审查退回里只要有 `题面类`（要改 `instruction.md`、`environment/` 或 `tests/`），且题已有达标版本，就不改题、不重跑。状态改为 `阻塞（<机器名>）：达标版本保护——审查要求改题面 <条目>；解除条件：人类决定驳回该条，或批准另做 v<N+1> 并行重校准`，commit，push，回报详情 `blob` 链接，继续领下一题。
5. **人类批准做新版本时**：v<N> 的冻结包原样保留。v<N+1> 达标并通过审查，才另加一行 `达标版本` 替换交付；v<N+1> 不达标时，台账 1 写 `不达标（v<N+1>；v<N> 达标结论不变）`，题的结论仍按 v<N> 走，不得因新版本失败把整题判为不达标。

## 步骤

1. **占题**：`git pull --rebase origin main`；读 `topics/<题号>.md`，状态必须是 `待执行` 或 `阻塞`，否则停下并把该文件的 GitHub 链接给人类（已在执行或已执行；`退回出题（首发解通过，…）` 的题属于出题侧，不领）。把状态改为 `执行中（<机器名>）`，commit，push；push 被拒就 pull 后重新检查状态。占到后取候选：人类指定的候选号，没指定取头部 `起始候选`，再没有就候选 1；记下“当前候选号”。在 `topics/<题号>.md` 的本机执行记录里加一行 `- **占题**：<时间，带时区>`；第 5 步第一次 `harbor run` 开始时再加 `- **首跑**：<时间，带时区>`。两行都随第 9 步一起推，用来统计“占题到首跑”。`task_id` 用候选里的“题目名”。占的是阻塞题且本机 `tasks/<题号>/` 已有产物时，从停下的那一步接着做，不重建。占的是**退回题**（头部有 `退回` 行）时：读其最新 `reviews/<文件>` 中标 `退回` 的条目，沿用本机 `tasks/<题号>/` 已有产物，只修这些条目，修法与版本规则同第 10 步第 4 条（校准类退回不修，直接按第 10 步第 3 条登记不达标）；第 9 步照常追加新台账行、复制新摘要，然后进入第 10 步。占的是**重判题**（状态 `待执行（重判，<本机名>）`，头部有 `- **重判**：` 行）时：判据已变而原结果按新判据可能达标，**不新跑任何模型、不改题包**；用本机 `tasks/<题号>/` 已有产物，按现行要求书重写 `evidence/calibration.md` 的“成功轨迹深度”与“结论”（原文保留，新判在后，注明重判日期与依据），判为达标就从第 7 步起做完 7、8、9（台账 1 追加新行），判为不达标直接第 9 步登记。占的是**补测题**（状态 `待执行（补测强模型，<本机名>）`，头部有 `- **补测**：` 行）时：原先因弱模型解出而停、强模型从没跑过，条件 B 取消后要补测。用本机 `tasks/<题号>/候选<N>/` 里补测行写明的版本题包，**不重建、不改题**；同一版本已有工程检查记录就沿用，不重做第 2–4 步；原弱模型运行保留为历史，不入判定；从第 5 步起只跑强模型（GPT 5.6 四次，0/4 再加 Astra 一次），然后照常第 6–10 步。本机找不到该版本题包 → 标 `阻塞（<机器名>）：补测题包缺失`，回报并领下一题。
2. **构建题包**（第二阶段 2.1）：按交付要求 §1 的树建目录；环境、离线、隔离与防泄漏按 2.1 其余条款。被试 agent 在断网容器里要用的工具（tmux、asciinema、Node、Codex 等）先看本机 `env-kit/` 有没有验证过的 Dockerfile 段，有就照抄，不重新摸索。有 `drafts/<题号>/` 时以它为起点：把题面、生成器、参考解、验证器复制进 `package/<task_id>/` 的对应位置，再做容器化、依赖固定与目录整理；先在容器里重跑一遍草稿 README 写的流程，奖励 1 才往下走。**红线：`drafts/`、整个 repo 和 `.env` 不得进入 Agent 镜像的构建上下文或容器**（镜像只从 `environment/` 构建）。题文件有 `## 构建简报` 时，题面、数据生成、依赖版本按简报第 1、2、5 小节做，简报是默认方案：实跑发现不可行或不对才偏离，每处偏离在 `topics/<题号>.md` 的本机执行记录里加一行 `- **简报偏离**：<小节> 原为 __，改为 __，原因 __`；简报没写而不得不自己定的，加 `- **简报缺口**：<小节> 自定 __`（第 7 小节“已知不确定点”定下来的也记为偏离）。没有简报的题照旧自行设计，并把主要自定项都记为简报缺口。这些记录与第 9 步同一 commit 推上去，供 `研究出题` 改进后续简报。
3. **写验证器与参考解**（第二阶段 2.2）：验证器按 2.2 四节；最终奖励二元。参考解入口 `solution/solve.sh`。有简报时子检查、容差、参考解算法、简化反例按简报第 3、4、6 小节起步，偏离与缺口同上记录；简报第 3 小节写了贴边容差推导的，冻结容差时（≥ 7 种子）**只准放宽、不准收紧**（要求书 2.2）。**首发解闸门**（2026-10-29 起，[对抗出题规范 D 节](../../flows/tb-science/adversarial-design.md#d-首发解)）：简报第 6 小节第一项标了“首发解”的题，参考解通过后、跑其他简化反例之前，先照简报写的算法实现首发解并在本题包里实跑一次（题目有 `drafts/<题号>/first_shot.py` 就直接用）。奖励 **1** → 这道题几乎必然 ≥ 3/4，**不进入第 4、5 步、不跑任何模型**：`git pull --rebase origin main`，把 `topics/<题号>.md` 状态改为 `退回出题（首发解通过，<机器名>）`，头部加一行 `- **退回出题**：<日期> 首发解 <一句话> 奖励 1，过了 <子检查列表>；待出题侧按对抗出题规范重写`，本机执行记录加一行同样内容，commit push；回报一行 `<题号> 退回出题（首发解通过），未跑模型`；本机 `tasks/<题号>/` 保留，领下一题。奖励 0 → 在 `evidence/engineering.md` 记首发解挂在哪个子检查，照常往下。简报里没有标首发解的旧题不适用闸门，照旧只跑合理简化反例。
4. **工程检查**（第三阶段 3.1）：按 3.1 原文列出的检查项逐项实际运行，结果写入 `evidence/engineering.md`，附命令、退出状态与日志路径。任何一项没有实际运行记录就不能进入下一步。
5. **模型校准**（第三阶段 3.2）。唯一入口是 `harbor run`：Harbor 用 `environment/` 起干净容器、在容器里新起被试 agent、独立容器判分、保存轨迹。本会话只发起和收集，不自己做题。固定顺序：
   1. 登记模型名单与层级，写进 `evidence/calibration.md`：强模型组 GPT 5.6 Sol (max)、GPT-6 Astra，agent 为 `codex`。2026-10-29 起**不跑弱模型**（甲方取消条件 B），名单不登记弱模型组；本机 `.env` 里有 `WEAK_*` 也不用。
   2. **直接跑强模型**（按“省力协议”第 2 条成批发起，用 `wait_runs.py` 等）`-a codex -m <GPT 5.6 Sol (max)>` 跑 4 次（容器内 Codex 凭据：`.env` 有 `OPENAI_API_KEY` 用它，没有则把本机 `~/.codex/auth.json` 传入容器，Harbor 0.25.0 用环境变量 `CODEX_AUTH_JSON_PATH` 指向它；两种都不行按“推进深度”处理，不换模型。任务是 `no-network`，容器里的 Codex 要连推理服务，加 `--allow-agent-host chatgpt.com --allow-agent-host auth.openai.com --allow-agent-host api.openai.com`，只放行这几个推理域名，不开通用代理；mac-a 实测可行且普通网站仍不通），存 `runs/<候选号>-gpt56-1..4/`；4 次都失败再跑 GPT-6 Astra 一次，存 `runs/<候选号>-gpt6-1/`。**提前收手**：有效成功累计达到 3 次时，不再发起剩下的 GPT 5.6 运行：已是 ≥ 3/4，条件 C（≤ 2/4）不可能满足，再跑只耗本机。已经在跑的并发运行不中断、照常记录；没发起的在 `evidence/calibration.md` 记 `提前收手，未运行`，通过数写 `≥ 3/4`（实际成功数在括号里），第 6 步判 `太简单` 不达标。成功被查出属于绕过的不计入这 3 次。无效失败按原记录保留并重跑该次。
   3. **每条强模型成功轨迹查绕过**：对照 [得分对应真实完成情况](../../specs/tb-science-requirements.md#22-验证器与评分) 列出的绕过路径查轨迹。属于绕过 → 回第 3 步修验证器，版本 +1，从第 4 步重来；不属于绕过 → 照常计入。
   4. 每次运行保存 [轨迹与运行记录](../../specs/tb-science-requirements.md#轨迹与运行记录验收标准-12) 表中的全部字段；步数取 Harbor 轨迹里的 agent 步数，字段名写进 `evidence/calibration.md` 的“步骤计数定义”。按 [校准结果要求](../../specs/tb-science-requirements.md#校准结果要求合并验收标准-11--交付要求-21) 判条件 A、C（条件 B 已取消），按 [成功轨迹深度](../../specs/tb-science-requirements.md#成功轨迹深度合并验收标准-11--交付要求-22) 判步数。
   5. 每次运行结束后立刻按 [templates/trajectory.md](templates/trajectory.md) 写该次的 `runs/<...>/summary.md`，按 [templates/run-metadata.json](templates/run-metadata.json) 写 `runs/<...>/metadata.json`，其中 `phase_seconds` 填环境构建、agent 安装、作答、判分四段用时（取自 Harbor `result.json`；第一次填时把 Harbor 实际字段名写进 `evidence/calibration.md` 的“步骤计数定义”下方），不留到最后补。运行目录里不得留 `auth.json` 或含密钥的 `.env`（交付包会原样带走运行目录）。
   - 第一次在本机跑之前，先 `harbor --help` 核对 agent 名、模型参数和 provider 的传入方式；与本文写法不一致时以本机实际版本为准，并把实际命令原样写进 `evidence/calibration.md`。然后用一个最小的 `network_mode = "no-network"` 任务跑一次 `harbor run -a oracle -n 1` 冒烟，退出码 0 才跑真题；失败多半是启动 prompt §0 的 WSL 内核问题，按“推进深度”自己修，到门槛才标阻塞。Harbor 0.25.0 已核对：`-a codex`（强模型）、`-a terminus-2`（原弱模型用，2026-10-29 起不再跑）、`-m <模型>`、`--base-url`、`--api-key-name`、`--api-format`（弱模型第三方 provider 用后三项，只对 terminus-2 有效；codex 只接受 `openai_responses`）、`--ae KEY=VALUE`（向容器内 agent 传环境变量）、`--allow-agent-host <域名>`（断网任务里放行 agent 的推理域名）。
6. **判定与分流**（先做一次 [规则同步](../../AGENTS.md#规则同步)，判据按最新规则）：
   - 条件 A、C 都满足（条件 B 已取消，下同），且**至少一条**成功轨迹 ≥ 60 步（[成功轨迹深度](../../specs/tb-science-requirements.md#成功轨迹深度合并验收标准-11--交付要求-22)；其余成功轨迹不要求）→ 达标，继续第 7 步。
   - 条件 A、C 都满足，没有 ≥ 60 步的成功轨迹，但最长成功轨迹 **50–59 步** → **近达标**（保护留存）。不补跑，**不换候选**，继续第 7–10 步。打包时用 `N` 标这条成功运行，不标 `D`，包名自动带 `-d50`。登记后整题结束，领下一题。近达标和达标分开登记、分开归档，不能混在一起；“达标版本保护”的全部条款同样适用。
   - 条件 A、C 都满足，但全部成功轨迹 < 50 步 → 不达标，**不补跑**：不追加 GPT 5.6 或 GPT-6 Astra 运行去凑深度，按下面“其余不达标”换候选，摘要留给 `复审改难`。
   - 失败原因属于 [运行独立与无效结果](../../specs/tb-science-requirements.md#运行独立与无效结果验收标准-13) 所列的无效情形 → 修复后重跑该运行，原记录保留在 `runs/`。
   - 题面或验证器有缺陷 → 回第 2–3 步修，然后从第 4 步重来，版本号加 1。只适用于还没有达标版本的题；已有达标版本的见“达标版本保护”。
   - 其余不达标（5.6 通过 3/4 或 4/4、太难、步数不足）→ 不改题；在 `evidence/calibration.md` 写明本候选结论，然后**换候选**：回第 1 步取下一个候选（不重新占题，状态仍是执行中），`task_id` 换成新候选的题目名，版本从 v1 起，原候选的 `package/`、`evidence/`、`runs/` 原样保留在 `<WORKDIR>/tasks/<题号>/候选<N>/` 下。
   - 三个候选都不达标 → 跳到第 8 步，整题登记为不达标。
7. **rubric 自检**（第四阶段 4.1）：对照官方 39 项 rubric 逐项标记通过 / 不通过 / 建议驳回，写入 `evidence/rubric.md`；“建议驳回”须写一句理由，由审查按 4.1 判定。
8. **整理证据与打包**（第四阶段 4.2）：填 `evidence/README.md`，证据表每一行给出文件路径；缺的标“待验证”，不写成已完成。达标题再按 [delivery.md](delivery.md) 打交付压缩包：`python3 repo/skills/tb-run/scripts/pack_delivery.py <WORKDIR>/tasks/<题号> --candidate <N> --version <N> --machine <机器名> --use <运行>=<判定> ...`（`--use` 只点名判定用的运行，见 delivery.md 第 3 节），再 `python3 repo/skills/tb-run/scripts/check_delivery.py <zip>`。自检输出 `ok` 才能按达标登记，并立即按“达标版本保护”第 1 条冻结；出 `FAIL` 就修对应材料（题包、`metadata.json`、`--use` 点名）后重打，修不了的按“推进深度”处理，不得跳过自检登记达标。
9. **登记**：做一次 [规则同步](../../AGENTS.md#规则同步)（含 `git pull --rebase origin main`；登记的判据按最新规则）；台账 1 追加一行（近达标的校准结果写 `近达标（50–59；强:… 5.6:…/4 步数:<最长成功步数>）`，与 `达标（…）` 分开）；改 `topics/<题号>.md` 状态（不达标改 `已执行-不达标`；达标和近达标先保持 `执行中（<机器名>）`，终态由第 10 步定）；把 `evidence/calibration.md` 复制为 `flows/tb-science/runs/<题号>/calibration.md`，把每个 `runs/<候选号>-<模型>-<序号>/summary.md` 复制为 `flows/tb-science/runs/<题号>/<候选号>-<模型>-<序号>.md`；达标题再把压缩包里的 `README.md` 复制为 `flows/tb-science/runs/<题号>/delivery-README.md`；运行 `python3 skills/tb-board/scripts/build_board.py` 刷新看板；一次 commit，push。回复人类：`<题号> 已执行，结果 <达标/近达标/不达标>`；台账 1 的 `blob` 链接；`flows/tb-science/runs/<题号>/` 的 `blob` 链接；本机路径与机器名（本机文件无 GitHub 链接）；达标题加交付压缩包的本机路径与 SHA-256（`pack_delivery.py` 打印的两行）；`规则版本 <规则版本>`（取法见 AGENTS.md“规则同步”）。链接按 AGENTS.md“回报链接”规则。结果为 `不达标` 时多一行 `不达标，不进入审查；摘要已上传供 复审改难`（太简单、太难、步数不足都一样）。回报后不等人类：达标题直接进入第 10 步，不达标题回去领下一题。
10. **自动审查与修复**：只对第 9 步登记为达标或近达标的题做（下文“达标”同时指两档，归档目录与回报措辞按档区分）；不达标题登记即结束，不审查。修复轮次 k 从 0 起，题状态全程保持 `执行中（<机器名>）`，别的对话不会领走。
    1. **起独立审查进程并等待**（按“省力协议”第 3 条等待）：在本 clone 下运行
       ```
       codex exec --cd <repo> "读 AGENTS.md，然后执行口令：审查 <题号>"
       ```
       它按 tb-review 写 `reviews/<题号>[-rN].md`、追加台账 2 并 push；每个退回项都标 `校准类` 或 `材料类`（见 [checklist](../tb-review/checklist.md)）。做题的本对话**不得自己审**，也不改审查结论。
    2. **通过**：
       - 把 `topics/<题号>.md` 状态改为 `已执行-达标`，加一行 `- **审查**：通过（修复 k 轮）`。
       - 近达标题的状态改为 `已执行-近达标`，不改为 `已执行-达标`。
       - 把最终交付 zip 复制到 `{{WORKDIR}}/deliveries/`（本机已通过审查的交付汇总目录；近达标档放 `{{WORKDIR}}/deliveries/near60/`），并把 `<SHA-256>  <zip 文件名>` 追加到该目录的 `SHA256SUMS.txt`。
       - 刷新看板，commit，push。
       - 回报：`<题号> 审查通过（修复 k 轮）`，近达标档写 `<题号> 审查通过（近达标档，最长成功 <步数> 步；修复 k 轮）`；zip 的本机路径与 SHA-256；审查详情的 `blob` 链接；`规则版本 <规则版本>`。
    3. **退回且含任一 `校准类`**：不修。
       - 台账 1 追加一行，校准结果写 `不达标（审查：<条目号>）`；状态改为 `已执行-不达标`，摘要留给 `复审改难`。
       - 回报 `<题号> 审查退回（校准类），已转复审改难`，加详情 `blob` 链接。
    4. **退回且全是 `材料类`**：k 加 1；k ≤ 3 时修，只修标为退回的条目。
       - 在 `topics/<题号>.md` 头部加 `- **退回**：reviews/<文件名> 退回 N 项（自动修复第 k 轮）`。
       - 只修材料（`evidence/`、`solution/*.md`、`task.toml [metadata]`、`rubric.md`、运行的 `metadata.json` / `summary.md`），不跑新模型。修的文件不在 zip 里时不重打包；在 zip 里时按“达标版本保护”第 3 条，从冻结 zip 重打包并核对 MANIFEST。
       - 这一轮退回里只要有 `题面类`，就不进本条，按“达标版本保护”第 4 条停下交人类。自动修复**永远不改** `instruction.md`、`environment/`、`tests/`，也不为修复重跑模型。
       - 修完回到第 9 步（台账 1 追加新行，校准结果后注明 `材料修复第 k 轮`），再回本步第 1 条重审。
    5. **修复 3 轮后仍退回**（第 4 次审查仍有材料类退回）：

       - 回报 `<题号> 审查退回 N 项`，加详情 `blob` 链接，然后继续领下一题。
    6. **`codex exec` 失败**（命令不存在、未登录、超时、没能 push）：按“推进深度”自己修。到门槛仍不行 → 题保持已登记的达标，状态改为 `已执行-达标`；回报一行 `自动审查未执行：<原因>`，留给人类在同机另开对话说 `审查` 补审；继续领题。
