# tb-review：审查

## 触发口令

- `审查`：在执行机上，把**本机所有已执行且达标、尚未审查**的题全部审一遍，逐条对照要求书判定，写审查详情并登记 [台账 2](../../flows/tb-science/ledger/reviews.md)。人类不用给题号。
- `审查 <题号>`：只审指定的一题。

**主路径是自动审查**：[tb-run](../tb-run/SKILL.md) 第 10 步在每道达标题登记后，起一个独立 `codex exec` 进程说 `审查 <题号>`。这个进程没有做题上下文，等同另开对话，审完由做题方按结论修复或收尾。人类说 `审查` 只用来补审：存量达标未审的题，或自动审查没起来的题。补审要在执行机上另开一个贴了同一启动 prompt 的 Codex 对话说，**不要在正在做题的那个 Codex 对话里审**。

## 目的

流水线唯一的审查门禁。只回答一个问题：提交的材料是否满足要求书已有条款。只审**达标**题：不达标题（太简单、太难、步数不足）在登记时就结束，它的轨迹摘要给 `复审改难` 用，不经审查。退回时把每项标成 `校准类` 或 `材料类`。材料类由原执行机在 tb-run 第 10 步自己修，最多 3 轮；校准类不修，转 `复审改难`。人类不必插手。

## 输入

| 文件 | 用途 |
| --- | --- |
| [台账 1](../../flows/tb-science/ledger/tasks.md) | 取本机执行过的题与本地路径 |
| [台账 2](../../flows/tb-science/ledger/reviews.md) | 判断哪些题还没审 |
| 本机交付压缩包、`package/<task_id>/instruction.md`、`evidence/` 下 `engineering.md`、`calibration.md`、`rubric.md`；题文件“相似性自查” | 被审材料，只读这些，见 [checklist.md](checklist.md) 开头 |
| [checklist.md](checklist.md) | 审查条目，每条链接到要求书原文 |
| [要求书](../../specs/tb-science-requirements.md) | 判定依据 |

## 输出

- `flows/tb-science/reviews/<题号>.md`（复审 `-r2`、`-r3`）：按 checklist 逐条给出 `通过` / `退回` / `不适用`，每条注明查看的文件路径；退回须引用要求书或官方 rubric 原句，并在“类别”列标 `校准类` / `题面类` / `材料类`。对已有达标版本的题标 `题面类`，必须引《验收标准》《交付要求》或官方 rubric guidance 原句（见 checklist）。审查对象以题头“达标版本”的冻结 zip 为准。
- 台账 2 每审一题追加一行。
- 退回时：题状态是 `执行中（…）`（自动审查）就不动状态和队列；否则（人类补审）把 `topics/<题号>.md` 状态改回待执行，并置顶 [queue.md](../../flows/tb-science/topics/queue.md)。
- `board.md` 刷新。全部 commit 并 push 到 `main`。

## 步骤

1. `git pull --rebase origin main`。列出**待审题号**：台账 1 中“执行机”等于本机名**且“校准结果”以 `达标` 或 `近达标` 开头**的行对应的题号，其达标与近达标行数之和 > 在台账 2 中结论不是 `阻塞` 的行数（一次达标登记对应一次审查）。校准结果为 `不达标` 的行永不列入。`审查 <题号>` 时只取那一题，且不受上面的计数限制（人类点名或决策表要求重审时用）。没有 → 回报一行 `<机器名> 无待审查题目`，结束。
2. 对每个待审题号，依次做第 3–6 步，一题审完再审下一题。
3. 占审：`reviews/<题号>.md` 不存在就用它，存在就用下一个 `-rN`；先写一个只含“审查中（<审查者>，<时间>）”的文件，commit，push；push 被拒就 pull 后重新取编号。占到后再开始审。台账 1 给的本地路径本机读不到 → 结论 `阻塞`，详情写明机器名与路径，登记后跳到下一题。
4. 按 [checklist.md](checklist.md) 审，顺序固定，不复跑任何东西：
   1. **盲读**：先只读 `instruction.md` 和它指明的作答可见资料，不看 `solution/`、`tests/`、`evidence/`；写“不看参考解的独立审题”记录（≤ 5 行）。
   2. **G1**：对交付压缩包跑 `check_delivery.py`，`ok` 即通过。
   3. **G2–G8**：只读 checklist 开头列的文件和段落，每条写一两句结论和所看文件。
   4. 写“独立领域复核”记录（≤ 5 行），复核者“AI，独立会话，未参与出题”。

   每条判定只有三种：
   - `通过`：满足所引原句。
   - `退回`：G1–G8 某条不满足；写出原句和不符之处。两段记录里发现的问题落在 G2–G8 的，按对应条退回。
   - `不适用`：原句自带的适用条件本题不满足；写出理由。

   《质量标准》的其余证据不逐条审，缺了只在 `evidence/README.md` 中标“待验证”，不退回、不进回报。
5. 结论：没有 `退回` → `通过`；否则 `退回`，退回项数 = 退回条目数。写详情文件（开头写明深度档：`达标档（≥ 60）` 或 `近达标档（50–59，包名带 -d50）`，以 `check_delivery.py` 的输出为准；8 行表，列为 编号 / 判定 / 类别 / 依据与所看文件，类别只在退回行填；加两段记录），台账 2 追加一行。
6. 结论为 `退回`，且题头部状态**不是** `执行中（…）`（即人类补审，不是 tb-run 第 10 步的自动审查）时另做；自动审查时跳过本步，由做题方处理：把 `topics/<题号>.md` 头部状态改为 `待执行（退回，<执行机>）`，并加一行 `- **退回**：reviews/<文件名> 退回 N 项`（写成指向 `../reviews/<文件名>` 的相对链接）（已有退回行就在其后再加一行，不删旧的）；把该题插到 queue.md 第 1 位，起始候选照原文件，理由“审查退回，优先修复”。
7. 全部待审题处理完：`git pull --rebase origin main`，运行 `python3 skills/tb-board/scripts/build_board.py`，一次 commit，push。
8. 回报：每题一行 `<题号> 审查 <通过/退回 N 项/阻塞>` 加详情文件 `blob` 链接；末行台账 2 的 `blob` 链接。链接按 AGENTS.md“回报链接”规则。

## 边界

- 只判 checklist 里的条目，不新增条目，不给要求书之外的建议和改进意见。
- 不复跑实验、不重写代码；只读 checklist 开头列的文件和脚本输出，不展开读其他材料。审查的目的是以最小成本确认符合官方硬性条款，不是复核全部工作。
- rubric 不通过或执行单元标“建议驳回”的项：属于“不影响科学任务核心、训练效果的、无关紧要”范围（交付要求 §3 原文）的，审查直接驳回并写一句理由，不自行加严，也不挂起等人。
- 审查方不得是做这道题的那个 Codex 对话或进程。

## 完成判据

- 每份详情文件有 G1–G8 共 8 行判定和两段短记录；`退回` 只出现在 G1–G8，且每个退回行都有类别。
- 本机每道已执行题的台账 1 行数 ≤ 台账 2 行数（即没有漏审），新行都在 `main` 上，详情链接可达。
- 人类补审退回的题在 queue.md 第 1 位且状态为 `待执行（退回，<执行机>）`；自动审查退回的题状态仍为 `执行中（<执行机>）`。
