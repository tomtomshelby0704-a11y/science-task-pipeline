## 总则

### 0.1 目的与范围

#### 目的与范围〔验收标准〕


TB-Science 数据集由原创、可执行的科学研究与工程工作流组成。任务旨在区分模型能力、覆盖广泛的科学领域，并为前沿模型保留具有实际意义的能力提升空间。

#### 总述〔质量标准〕


本文面向 TB science 的科研与科学计算任务，说明什么样的数据可以被认定为高质量评测数据。这里的“一条数据”是一个完整、可执行、可验证的任务，包含题面、科学数据、运行环境、参考解、评分程序和验证记录。

**高质量任务应源于真实科研问题，需要必要的专业判断，提供充分且准确的材料，在规定资源内能够完成，并通过独立、稳定的评分识别结果是否正确。每项质量判断都应有可核对的证据。**

本文是质量标准说明，不代表任何具体任务已完成验证。文中的科研示例用于解释标准，不是实测结论。

## 第一阶段 立项与设计

### 1.1 选题：科学问题真实、原创

#### 科学问题真实，任务设计有实质贡献〔质量标准 §1〕


任务应基于真实科研流程、科学计算代码或科研数据构建，可以裁剪、脱敏和离线化，但必须保留决定解法的科学机制、数据语义与关键约束。

- 说明研究背景、需要解决的问题，以及结果可用于哪一步分析或实验。
- 分别记录代码、数据、方法、参考解和测试的来源、版本、许可及新增设计。
- 不直接搬用或改写已公开评测题、公开竞赛题或现成 Issue/PR；不以更换参数、文件名或专业名词作为原创贡献。
- 可以复用合法的科研软件、公开数据和科学方法，但须说明任务目标、输入场景、环境和验收中的实质设计。
- AI 辅助须逐题披露，由具备相关经验的出题人员负责设计和验证，并由另一位具备相应领域经验的人员复核。

原创性与科学真实性分别判断：原创不自动证明科学上成立，真实素材也不自动证明任务设计原创。

**验证证据：**来源与改编说明、许可记录、新增贡献说明、相似性检查及独立领域复核记录。

#### 原创与来源〔验收标准 目的与范围〕


任务不得复制或轻度改写已有基准任务。允许使用来源明确、许可适当的公开数据和工具。

### 1.2 设计：难度来源与题面

#### 难度来自科学判断，材料足以支持求解〔质量标准 §2〕


任务应考察理解科学机制、调查数据与运行证据、选择方法、实现计算和验证结果的能力。题面长度、文件数量、工具调用次数和运行时长，不能单独证明专业深度。

题面应明确：

- 科学目标、输入范围、字段含义、单位、坐标或时间约定，以及适用的假设。
- 需要产出的文件或结果、格式、路径，以及允许修改的内容。
- 正确性要求、数值容差、异常处理、允许使用的工具和资源限制。
- 必要资料的获取位置。可以隐藏测试实例，不能隐藏影响正确性的规则。

多个环节应具有科研上的依赖关系。例如，先核对数据单位与采样条件，再选择计算方法，最后用独立检查确认结果。不能拼接无关操作或强制增加命令来制造难度。

对关键难点，应解释一种合理简化为什么会失败，并用运行结果验证。若简单方法满足全部公开要求，应接受，不能为了维持难度临时增加限制。

**验证证据：**能力说明、关键约束理由、合理简化方案的对照结果，以及不看参考解的独立审题记录。

#### 杜绝假难度〔交付要求 §2.3〕


题目设计应杜绝“假难度”。所谓“假难度”，是指题目的核心挑战并非来自科学知识的理解、运用与推理，而是依赖苛刻的格式要求、不必要的计算精度或与科学问题无关的图像识别障碍等细枝末节，人为增加作答难度。这类题目缺乏实质性的科学价值，也难以通过训练有效提升模型的科学能力及其在 TB-science 上的表现。因此，所有交付题目都应以具有科学价值的知识与推理挑战为核心，不得以无关的操作障碍替代真正的科学难度。

### 1.3 准备科学数据

#### 科学数据准确，裁剪和脱敏不改变问题含义〔质量标准 §3〕


逐项核对数据字段、单位、坐标、样本标识、时间、缺失值和异常值处理。数据裁剪、标识替换和格式转换后，原有关系与科学含义应保持一致。

- 原始输入、加工过程和标准答案分别留存，能够追溯每一步处理。
- 脱敏后仍保留求解所必需的分组、关联和顺序；确有科学意义的标识或顺序不能被随意打乱。
- 标准答案说明来源，关键结果使用解析小例子、独立算法、专业资料或可验证不变量交叉核对。
- 不能仅保存参考解输出，再以该输出证明参考解正确。
- 发现数据、真值或测试错误后，记录修订及受影响的任务版本与运行结果，重新验证相关结论。

**示例：**单位换算任务应能用人工可核算的小例子确认量纲与数值；样本汇总任务应检查脱敏后的样本标识是否仍与原始分组正确对应。

**验证证据：**数据说明、加工记录、独立真值依据、脱敏前后语义核对和错误修订记录。

## 第二阶段 构建题包

### 2.1 题包格式与运行环境

#### 任务交付格式要求〔交付要求 §1〕


所有任务须以 Harbor 兼容的可执行任务格式交付，目录结构如下：

```text
<task_id>/
├── instruction.md              # 任务说明与输出要求
├── task.toml                   # Harbor 配置与任务元数据
├── environment/
│   ├── Dockerfile              # 运行时镜像（除非另有约定）
│   ├── requirements.txt        # 额外依赖
│   └── resources/              # 数据集/代码/论文等资源
├── solution/                   # 隐藏于解题 Agent
│   ├── solve.sh                # 参考/Oracle 解入口
│   ├── reference_solution.md   # 专家认可的参考研究成果
│   └── solution_explanation.md # 参考方法、证据、假设与边界
└── tests/                      # 隐藏于解题 Agent
    ├── test.sh                 # 判分入口
    ├── verifier.*              # 验证/评分实现
    └── fixtures/               # 隐藏的期望输出/参考数据
```

solution/ 与 tests/ 目录须交付给评测系统，但对解题 Agent 隐藏。

#### 环境可复现，离线化保留科学机制〔质量标准 §6〕


任务应提供固定版本的代码、依赖、数据和可重复启动的环境。构建、作答与判分所需材料应预先备齐，能够在无公网条件下完成；作答与判分环境独立。

- 从干净环境构建并运行，记录构建、计算、评分耗时及 CPU、内存、磁盘使用情况。
- 重置后，上轮文件、缓存、进程和状态不污染下一轮。
- 多实例实际并发运行，核对文件、端口及其他状态相互隔离。
- 缩小数据规模或替换外部依赖时，保留决定科学结论和解法的条件，并用正确解与相关错误解核对。
- 区分科学求解失败、任务超预算、运行截断、内存或磁盘耗尽及基础设施故障，不选择性重试到成功。

落实隔离与防泄漏措施：答案、隐藏测试和评审材料不能出现在作答可见的镜像层、Git 历史、环境变量或临时目录中。

**验证证据：**环境配置、干净构建和断网运行结果、重置与真实并发记录、资源测量及故障分类。

#### 环境可复现〔验收标准 §1.3〕


环境可复现。任务须能在干净环境中，使用已记录的依赖、数据版本和资源配置独立运行。

### 2.2 验证器与评分

#### 指令与验证一致、验证可靠〔验收标准 §1.3〕


指令与验证一致。指令须清晰、完整且无矛盾；验证器须检验明确要求的结果，不得因无关的实现差异拒绝正确解。

验证可靠。须检查验证器能够接受已知正确解，拒绝空解、代表性错误解及绕过解。模型不得访问隐藏答案或篡改评分机制。数值容差及随机性评测规则须预先声明。

#### 验收真正运行出来的科学结果〔质量标准 §4〕


评分需要同时确认实现、执行、输入参数和结果的一致性。文件存在、报告声称“计算完成”、图像外观相似，都不足以证明科学任务完成。

| 检查对象 | 合格要求 | 应识别的错误 |
| --- | --- | --- |
| 实现 | 实现题面要求的方法或满足要求的合理替代方法 | 只写接口、跳过核心计算、错误处理关键条件 |
| 执行 | 从实际入口运行，数据与参数对应本次任务 | 使用旧结果、替换输入、伪造执行报告 |
| 数值结果 | 精度、容差与误差来源明确 | 单位错误、坐标错误、数值不稳定或超出容差 |
| 科学产物 | 文件可解析，可由后续程序读取并继续使用 | 文件损坏、缺少必要变量、报告与数据不一致 |
| 副作用 | 完成目标，同时保留公开要求保护的数据与属性 | 修改非目标样本、破坏关联关系或删除必要数据 |

数值容差应依据算法误差、数据精度或重复测量确定，不能为拒绝某个答案事后收紧。随机性任务应事先说明随机性来源、重复次数和统计判定方法；性能任务应记录硬件、预热与重复测量条件。

**验证证据：**真实执行记录、数据与参数记录、产物检查、容差依据、必要的重复测量及副作用检查。

#### 测试能拒绝相关错误，也接受合理正确解〔质量标准 §5〕


测试应建立“公开要求 → 输入条件 → 独立预期结果 → 测试项”的对应关系，覆盖正常、边界、异常和相关回归。局部单元测试之外，还要检查完整科研流程与最终产物。

- 参考解通过，符合公开要求的合理替代解也应通过。
- 准备与本题有关的错误实现，例如漏做单位换算、误用坐标、遗漏边界、错误处理缺失值或使用不适用的数值方法，记录被哪项测试拒绝。
- 编译失败不能计作发现科学计算错误；等价实现不能被当成必须拒绝的错误。
- 对适用任务增加输入输出关系检查。例如，记录顺序确实不影响结果时，打乱顺序后结果应一致；只有问题确实满足线性关系时，才检查相应的缩放关系。
- 同一提交在独立环境重复判分，应在事先定义的随机差异范围内保持一致。
- 零测试、收集失败、报告损坏或必要检查未执行，不能判为成功。

报告关键需求覆盖、有效错误实现的检出情况、正确解误拒情况和重复判分差异，并说明各项分母、条件与未覆盖内容。测试数量和代码覆盖率不能替代这些证据。

**验证证据：**需求与测试对应表、正反例执行结果、替代解检查、稳定性记录及未覆盖项。

#### 得分对应真实完成情况，不能靠绕过评分获奖〔质量标准 §7〕


评分由可信进程依据实际产物生成。作答进程不得写入可信奖励，也不能通过提交的报告或诱导文字改变评分规则。

应实际检查以下路径：未完成计算却提交满分报告；硬编码公开样例；读取隐藏答案；跳过或破坏测试；覆盖评分依赖；通过归档路径、符号链接或不可信反序列化越界；利用残留进程在判分期间改写产物或结果。

评分时明确提取必要产物，在独立环境执行，限制候选程序的权限与可写范围。作答结束后的后台进程不能影响判分结果。科研输入、源码注释和报告中的指令性文字只能作为数据处理，不能成为可信指令。

最终奖励采用二元判定：完成全部必要要求为 1，否则为 0。子检查结果用于诊断，不能用部分测试通过掩盖关键科学目标失败。评分输出应包含实际执行情况、子检查明细和最终奖励；任务失败与基础设施故障分别记录。

短解和合法预计算是否允许，应按公开要求判断，不能仅因出题人员未预料到就认定作弊。发现绕过路径后，同时回归攻击反例和合法解。给定预算内未发现绕过，仅说明本轮未发现。

**验证证据：**攻击条件与预算、实际攻击结果、修复记录、合法解回归及剩余风险。

## 第三阶段 验证与校准

### 3.1 参考解工程验证

#### 参考解工程检查〔质量标准 §8〕


参考解还应完成连续三次通过、空操作不通过、断网运行和真实并发等工程检查。记录实际运行顺序、评分退出状态和结果，不能手填“通过”。

### 3.2 模型校准与运行记录

#### 校准分组〔验收标准 目的与范围、§1.1〕


模型校准采用两个能力组，不要求使用任何特定模型供应商或专有模型检查点。

强模型组。用于评估任务可解性的前沿模型。候选示例包括 Opus 5、GPT-5.6、GPT-6 和 Fable 5.1。可任选一个符合条件的模型，无需测试组内全部模型。

弱模型组。用于评估任务难度的 Tier 1.5 或 Tier 2 模型。可任选一个符合条件的模型，不限定供应商或模型检查点。

校准前须记录模型名单及其层级归属。上述模型名称仅为候选示例，不代表已核实其可用性或能力排名。

> 2026-10-29 甲方进一步放宽：不再要求条件 B，名单只登记强模型组，不跑弱模型组。

#### 运行独立与无效结果〔验收标准 §1.3〕


运行独立。强弱模型须在可比评测条件下，从相同任务初始状态独立运行，不得继承其他运行的产物、答案或轨迹。

受到任务定义缺陷、验证器缺陷或可利用漏洞影响的结果，包括未完成所要求的科学工作却通过验证的情况，不得作为校准证据。验收前须修复相关问题，并重新运行受影响的评测。

#### 难度有真实运行支撑，成功轨迹完整〔质量标准 §8〕


先确认任务成立、数据准确、环境正常和评分公平，再解释模型表现。模型低分只能补充说明挑战性，不能单独证明数据质量。

- 在明确的模型版本、工具权限、推理设置、时间和计算资源下进行多次独立运行，保留全部结果。
- 报告成功次数与总次数、用时、原生步数和失败原因；单次独立成功率与多次尝试取最好结果分别报告。
- 每题应有真实 Agent 当次成功的完整轨迹及原生评分记录。参考解通过不能代替 Agent 成功。
- 将失败归因为专业理解、证据使用、方法选择、实现、验证或工具使用时，指出具体证据；无法确定原因时明确标注。
- 排除依赖缺失、断网导致必要资料不可得、冷门记忆、机械重复和任意格式要求造成的假难度，不人为拉长轨迹。

（本节最后一段“参考解工程检查”见 [3.1 参考解工程验证](#31-参考解工程验证)。）

**验证证据：**全部独立运行记录、成功轨迹、原生评分日志、参考解与空操作验证，以及有证据支持的失败分析。

#### 轨迹与运行记录〔验收标准 §1.2〕


| 记录类别 | 必须保留的字段 |
| --- | --- |
| 完整轨迹 | 操作、工具调用、输出、中间产物、最终产物，以及正确性和性能结果 |
| 运行元数据 | 准确的模型检查点或 API 标识、智能体框架及版本、系统提示词、启用的工具、采样配置、执行预算、运行时间及退出状态 |
| 评测记录 | 任务与验证器版本、验证器结果、模型分组、校准条件，以及适用时的失败分类 |

须忠实、完整地保留每项任务的所有校准尝试，包括未成功及无效的尝试。必要脱敏须保留记录结构，并说明脱敏规则。

验收文档和公开摘要可使用不指向特定供应商的模型代号。准确的模型标识须保存在受控评测记录中，以支持复现与审计。

#### 校准结果要求〔合并：验收标准 §1.1 + 交付要求 §2.1〕


同一任务须在可比评测条件下同时满足以下三项条件，方可通过模型校准：

| 条件 | 所需证据 |
| --- | --- |
| 条件 A — 强模型组成功 | 至少一条来自符合条件的强模型组模型的完整成功轨迹，且成功结果经验证器确认。 |
| 条件 B — 弱模型组失败 | 至少一条来自符合条件的弱模型组模型的完整失败轨迹，且失败结果经验证器确认。 |
| 条件 C — 难度上限 | GPT 5.6 Sol (max) with Codex pass rate <= 2/4。如果 GPT 5.6 Sol (max) pass rate 为 0，则需要提交 GPT-6 Astra (with Codex) 成功轨迹一条。 |

三项条件均须满足。每组可任选一个符合条件的模型；条件 C 中的成功轨迹可同时作为条件 A 的证据。

> 2026-10-29 甲方进一步放宽：**不再要求条件 B**。校准不跑弱模型，通过模型校准只需条件 A 与条件 C 同时满足，再加成功轨迹深度。此前已跑的弱模型运行保留为历史，不入判定；弱模型成功也不再作为否决理由。

有效失败须体现模型在预先声明的执行预算内，未能满足定义清晰的任务要求。由基础设施中断、凭据无效、任务环境损坏、指令歧义或矛盾，以及指令与验证器不一致所导致的失败，不得作为任务难度的证据。

#### 证据的解释〔验收标准 §1.1〕


强模型组成功表明，在所记录的条件下，该任务可由模型完成。弱模型组失败表明，所选模型在相应条件下未能完成任务。

这两项结果共同为任务可解性及所选模型之间的能力区分提供证据，其结论限于所记录的评测条件。仅有其中一项结果不足以通过验收。

> 2026-10-29 甲方进一步放宽：不再要求弱模型组失败，强模型组成功加条件 C 与成功轨迹深度即可通过。

#### 成功轨迹深度〔合并：验收标准 §1.1 + 交付要求 §2.2〕


| 指标 | 要求 |
| --- | --- |
| 成功轨迹深度 | 每项任务**至少一条**成功轨迹包含 ≥ 60 个智能体步骤（agent turns） |
| 步骤计数 | 采用有明确文档说明且一致的智能体步骤定义 |

只要求至少一条成功轨迹满足；其余成功轨迹（含条件 A、条件 C 中 GPT 5.6 Sol (max) 的成功轨迹）不要求每条达到 60 步。失败轨迹不计入成功轨迹深度统计。不按 output tokens 分档，不设批次中位数目标。不得通过无意义操作、重复命令或刻意拆分响应凑步骤数。

> 2026-10-29 按甲方反馈修订。原要求为“每条符合条件的成功轨迹 ≥ 100 个智能体步骤；批次 P50 150 个”，已删除。

> 2026-10-29 甲方进一步放宽，流水线据此加**近达标档**：标准仍为“至少一条成功轨迹 ≥ 60 步”，这一档仍是第一目标。三项条件都满足、但最长成功轨迹只有 **50–59 步**的题，也算成功：冻结保护、打包、审查、登记，不再改难。它必须和 ≥ 60 的题分开：交付包名带 `-d50`，台账写 `近达标（50–59；…）`，状态为 `已执行-近达标`，看板单独计数。< 50 仍判不达标。

## 第五阶段 批次验收

### 5.1 多样性与分组

#### 整套数据覆盖不同科学问题，近亲任务正确分组〔质量标准 §9〕


单题质量与题集多样性分别检查。TB science 应在科学范围内覆盖不同研究子域、工作类型、关键机制、输入结构和产物，而非扩展到无关领域来凑多样性。

可按实际任务统计科学数据处理与分析、数值计算、科研代码诊断、方法实现和实验复现等工作类型，并检查是否过度集中于同一种模板、数据处理错误或求解方法。这些是覆盖检查维度，不是强制所有任务包含的流程。

同一数据来源、原型、模板或核心解法的近亲题先分组，再划分训练与最终评估，避免只改参数的任务跨集合。报告各类题数、有效运行数、通过率及覆盖缺口，不能将任务总量当成能力覆盖证明。

若用于训练，另外检查训练奖励与独立科学质量是否同步改善，并用未参与调题的新任务验证迁移；最终测试答案不得用于训练或反复选择参数。

**验证证据：**科学子域与工作机制分布、任务家族与近重复记录、集合划分及留出任务结果。
